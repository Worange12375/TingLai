# 听籁 SoundVerse · 识别服务容器部署指导方案

> 这份文档是**照着做就能跑通**的操作手册，面向要在自己服务器上手动部署识别服务的人。
> 不需要懂 Python，不需要懂 BirdNET，跟着章节顺序一步步敲命令即可。
>
> 如果你想了解服务的设计原理、接口契约、识别链路数据流，看隔壁的 `server/DEPLOY_GUIDE.md`。
> 这份只讲「怎么做」。

---

## 零、先明确目标和现状

### 做完这件事之后会怎样

前端「识籁」页面用户录一段鸟叫 → 音频发到你服务器上的识别服务 → 返回真实的 Top-3 物种和置信度 → 页面渲染对应科普卡。

### 不做会怎样（重要，不要慌）

**前端在没有识别服务的情况下也能正常打开、正常演示。**

识别请求失败时，前端会走「诚实兜底」：给出一组带明确「离线示例结果」标识的 Top-3，页面不白屏、不报错、不假装是真实模型输出。

所以这次部署是**把演示从「兜底模式」升级成「真识别模式」**，不是救火。可以从容做，做砸了随时 `docker compose down` 退回原状，前端不受影响。

### 一共分五步

| 步骤 | 做什么 | 大概耗时 |
|------|--------|----------|
| 第一步 | 服务器拉最新代码 | 1 分钟 |
| 第二步 | 启动 Docker 容器 | 5–15 分钟（首次要下模型） |
| 第三步 | 让外网能访问到这个服务 | 5 分钟 |
| 第四步 | 告诉前端「服务在哪」 | 2 分钟 |
| 第五步 | 重新构建前端并部署 | 3 分钟 |

## 一、开工前的前提检查

在服务器上逐条确认，**四条全绿再往下走**，否则中途会卡住。

### 1. Docker 装好了吗

```bash
docker --version
docker compose version
```

两条都要有版本号输出。注意是 `docker compose`（中间空格，Docker 官方新版插件），不是老的 `docker-compose`。
如果只有老版 `docker-compose`，后文所有 `docker compose` 命令换成 `docker-compose` 也能用。

如果没装：

```bash
# Ubuntu / Debian
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
```

### 2. 服务器能出网吗

构建镜像要拉 Python 基础镜像、装 ffmpeg、装 pip 依赖；首次启动还要下载 BirdNET 模型（约 50MB）。

```bash
curl -I https://pypi.org --max-time 10
```

有 HTTP 响应就行。如果服务器完全不能出网，直接跳到 **第七章「模型拉不下来怎么办」** 看离线方案，别硬试。

### 3. 磁盘够吗

镜像 + 依赖 + 模型合计约 **2GB**。

```bash
df -h /
```

建议留 5GB 以上余量。

### 4. 域名和证书

`tinglai.dushiofcourses.cn` 已经解析到这台服务器、并且配好了 HTTPS 证书。

> **为什么必须 HTTPS**：前端站点是 HTTPS 的。浏览器不允许 HTTPS 页面去请求 HTTP 接口（混合内容会被直接拦掉）。所以识别服务对外也必须是 `https://`。

## 二、第一步：拉最新代码

```bash
# 进到仓库目录（换成你服务器上的实际路径）
cd /path/to/SoundVerse

git pull origin main
```

拉完确认这几个文件都在，缺一个都跑不起来：

```bash
ls server/
```

期望看到（至少包含）：

```
Dockerfile              ← 镜像构建脚本
docker-compose.yml      ← 编排配置
requirements.txt        ← Python 依赖清单
recognize_service.py    ← HTTP 服务本体
birdnet_engine.py       ← BirdNET 引擎封装
```

**这些文件仓库里已经备齐了，你不需要自己写任何配置。**

## 三、第二步：启动容器

```bash
cd server
docker compose up -d --build
```

参数说明：
- `up` 启动
- `-d` 后台运行（不占着你的终端）
- `--build` 构建镜像（第一次必须加；以后只要代码变了也要加）

### 盯着日志看它起没起来

```bash
docker compose logs -f
```

（看够了按 `Ctrl + C` 退出看日志，**不会停掉服务**，服务在后台继续跑。）

正常情况下你会依次看到：

```
正在加载 BirdNET 模型（首次运行会下载约 50MB，请耐心等待）…
BirdNET 模型加载完成，识别引擎就绪。
识别服务启动，允许来源：https://tinglai.dushiofcourses.cn, ...
Uvicorn running on http://0.0.0.0:8000
```

**首次构建 + 下模型，5 到 15 分钟都算正常**，别以为卡死了就 Ctrl+C 掐掉。第二次启动几秒就好（模型缓存在 Docker 卷里，重建容器不会重新下）。

### 确认服务活着

```bash
curl http://127.0.0.1:8000/healthz
```

期望返回：

```json
{"status":"ok","engine":"ready","detail":"BirdNET 模型已加载"}
```

`engine` 字段三种取值，含义不同：

| 值 | 含义 | 要处理吗 |
|----|------|----------|
| `ready` | 模型已加载，可以真识别 | 不用，这就对了 |
| `lazy` | 模型还没加载，第一个请求时才加载（会慢几秒） | 不用，正常现象 |
| `error` | 模型加载失败，识别会返回 503 | **要**，看第七章 |

> 注意路径是 `/healthz` 不是 `/health`，多一个 z，别打错了。

### 常用运维命令

```bash
docker compose ps          # 看容器状态
docker compose logs -f     # 实时日志
docker compose restart     # 重启
docker compose down        # 停止并删除容器（模型缓存卷保留，下次起来还是很快）
docker compose up -d --build   # 改了代码后重新构建启动
```

## 四、第三步：让外网访问到这个服务

### 先理解现在的状态

`docker-compose.yml` 里端口是这么写的：

```yaml
ports:
  - "127.0.0.1:8000:8000"
```

`127.0.0.1:` 这个前缀意味着：**容器只绑在本机回环，外网现在访问不到**。这是刻意的安全设计——识别服务没有鉴权，直接裸奔在公网上会被人白嫖算力。

所以你要在下面两个方案里选一个。

---

### 方案 A：nginx 反向代理（推荐，正式演示用这个）

思路：外网 → nginx（443 端口，带 HTTPS 证书）→ 转发到本机 8000。

在 nginx 里 `tinglai.dushiofcourses.cn` 这个 server 块中，加上这段：

```nginx
server {
    listen 443 ssl;
    server_name tinglai.dushiofcourses.cn;

    # ...你原有的证书配置、前端静态文件配置保持不动...

    # 识别服务反代
    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 音频上传可能有十几 MB，别被默认 1MB 卡掉
        client_max_body_size 25m;

        # 模型冷启动 + 推理可能要几十秒，超时给足
        proxy_read_timeout  120s;
        proxy_send_timeout  120s;
    }

    # 健康检查（可选，方便你在浏览器里直接看状态）
    location /healthz {
        proxy_pass http://127.0.0.1:8000/healthz;
    }
}
```

改完检查语法再重载：

```bash
sudo nginx -t          # 必须先测，语法错了 reload 会挂掉整个站
sudo systemctl reload nginx
```

**方案 A 的最大好处**：前端和识别接口同一个域名，属于「同源」，浏览器根本不会触发跨域检查，CORS 问题直接不存在。省心。

---

### 方案 B：直接暴露端口（临时调试用，不建议长期开着）

改 `server/docker-compose.yml`，把 `127.0.0.1:` 前缀去掉：

```yaml
ports:
  - "8000:8000"          # 原来是 "127.0.0.1:8000:8000"
```

然后重启并放行防火墙：

```bash
docker compose up -d
sudo ufw allow 8000/tcp        # 用 ufw 的话
```

**方案 B 的三个坑，用之前想清楚：**

1. 这样暴露出来的是 **HTTP**，不是 HTTPS。HTTPS 的前端页面调不了 HTTP 接口，浏览器会拦。所以方案 B 只能用于 `curl` 调试或本地开发，**不能给正式站用**。
2. 服务无鉴权，公网上谁都能调。
3. 云服务器还要在**控制台安全组**里也放行 8000，光改 ufw 不够。

**结论：调试用 B，演示用 A。**

## 五、第四步：告诉前端「服务在哪」

### ⚠️ 这一步最容易配错，请逐字看完

前端通过环境变量 `VITE_RECOGNIZE_API` 找识别服务。**它填的是「服务基址」，不是完整接口地址。**

代码里（`src/lib/recognize.ts`）的逻辑是这样的：

```
最终请求地址 = VITE_RECOGNIZE_API 的值 + "/api/recognize"
```

也就是说 `/api/recognize` 这段是**前端自动补上的**，你不要自己再写一遍。

| 你填的值 | 前端实际请求的地址 | 对不对 |
|----------|-------------------|--------|
| （不填） | `/api/recognize`（同源相对路径） | ✅ 对 |
| `https://tinglai.dushiofcourses.cn` | `https://tinglai.dushiofcourses.cn/api/recognize` | ✅ 对 |
| `https://tinglai.dushiofcourses.cn/api/recognize` | `https://tinglai.dushiofcourses.cn/api/recognize/api/recognize` | ❌ **错，404** |

**记住一句话：`VITE_RECOGNIZE_API` 只填到域名（和端口）为止，后面什么都不加。**

### 怎么配

在**仓库根目录**（不是 server/ 目录）新建 `.env` 文件：

```bash
cd /path/to/SoundVerse       # 回到仓库根目录
vi .env
```

按你第三步选的方案，填对应的一行：

```bash
# ── 如果你选了方案 A（nginx 反代，识别接口和前端同域名）──
# 推荐：留空字符串，走同源相对路径，最省心
VITE_RECOGNIZE_API=

# ── 或者显式写全域名，效果一样 ──
# VITE_RECOGNIZE_API=https://tinglai.dushiofcourses.cn

# ── 如果识别服务在另一台机器/另一个域名 ──
# VITE_RECOGNIZE_API=https://api.你的域名.com

# ── 可选：识别超时毫秒数，默认 30000（30 秒）──
# 服务器性能弱、音频长，可以调到 60000
# VITE_RECOGNIZE_TIMEOUT=60000
```

> **补充：如果你的接口路径就是不叫 `/api/recognize`**（比如反代时改成了 `/recognize`），
> 那就别用 `VITE_RECOGNIZE_API`，改用 `VITE_BIRDNET_ENDPOINT`——这个变量填的是**完整接口地址**，前端会原样使用、不再拼接：
> ```bash
> VITE_BIRDNET_ENDPOINT=https://tinglai.dushiofcourses.cn/recognize
> ```
> 两个变量同时存在时，`VITE_BIRDNET_ENDPOINT` 优先。

### 另外注意

- `.env` 已经在 `.gitignore` 里，**不会被提交到 git**。这是对的（每台机器配置不同），但也意味着**换机器要重新建一次**。
- Vite 的环境变量是**构建时写死进产物**的，不是运行时读的。所以改了 `.env` **必须重新 `npm run build`** 才生效，光重启服务没有任何用。

## 六、第五步：重新构建前端并部署

```bash
cd /path/to/SoundVerse       # 仓库根目录

npm install                  # 如果依赖没装过或 package.json 变了
npm run build
```

构建产物在 `dist/` 目录。把它部署到你的静态托管位置：

```bash
# 举例：nginx 站点根目录是 /var/www/tinglai
sudo rm -rf /var/www/tinglai/*
sudo cp -r dist/* /var/www/tinglai/
```

> **小提醒**：项目用的是 HashRouter（地址形如 `https://站点/#/recognize`），
> 静态服务器**不需要**配 SPA 回退规则，刷新深层链接也不会 404。这块不用操心。

## 七、验证：怎么确认真的接上了

### 三级验证，从里到外

**第 1 级 · 服务本身活着**

```bash
curl http://127.0.0.1:8000/healthz
# 期望：{"status":"ok","engine":"ready",...}
```

**第 2 级 · 外网能访问到**

在**你自己电脑上**（不是服务器上）执行：

```bash
curl https://tinglai.dushiofcourses.cn/healthz
```

同样要看到 `status: ok`。失败说明 nginx 反代或防火墙没配对，回第三步。

也可以直接用浏览器打开 **`https://tinglai.dushiofcourses.cn/docs`**——这是 FastAPI 自动生成的交互式接口文档，能看到 `/api/recognize` 的完整参数说明，还能直接在网页上传音频测试。这个页面能打开，说明服务和反代都通了。

**第 3 级 · 前端真的走了真识别**

1. 浏览器打开 `https://tinglai.dushiofcourses.cn/#/recognize`
2. 按 `F12` 打开开发者工具，切到 **Network（网络）** 面板
3. 页面上录一段音（或上传一个音频文件），点识别
4. 在 Network 面板里找 `recognize` 这条请求：

| 看到什么 | 说明 |
|----------|------|
| 状态 `200`，响应里有 `detections` 数组 | ✅ **成功，真识别已生效** |
| 状态 `404` | 地址拼错了，八成是 `VITE_RECOGNIZE_API` 多写了 `/api/recognize`，回第五步 |
| 状态 `503` | 服务通了但模型没就绪，看第八章「模型拉不下来」 |
| 红色 CORS 报错 | 跨域被拦，看下一节 |
| 压根没有这条请求 | `.env` 没生效或没重新 build，回第五步 |

**最终判定**：页面结果区如果显示「离线示例结果」字样，说明还是在走兜底，没接上真识别。没有这个标识、直接给出物种和置信度，就是真的通了。

## 八、CORS 跨域说明

### 什么时候需要关心

- **选了方案 A（同域名反代）→ 完全不用关心**，同源不触发 CORS。
- **前端和识别服务不同域名 → 需要关心。**

### 服务已经放行了哪些来源

代码里（`server/recognize_service.py` 的 `ALLOWED_ORIGINS`）默认放行：

```
https://tinglai.dushiofcourses.cn      ← 生产站
http://tinglai.dushiofcourses.cn
http://localhost:5173                  ← 前端开发服务器
http://127.0.0.1:5173
http://localhost:8000
http://127.0.0.1:8000
http://localhost:4173                  ← npm run preview
```

### 换了域名怎么办（不用改代码、不用重建镜像）

**不要去改 Python 源码。**用环境变量追加就行。

编辑 `server/docker-compose.yml`，在 `environment:` 下面把注释掉的那行打开并填上你的域名：

```yaml
    environment:
      MAX_UPLOAD_MB: "20"
      WARMUP_ON_START: "1"
      LOG_LEVEL: "INFO"
      EXTRA_ORIGINS: "https://你的新域名.com,https://另一个域名.com"   # ← 加这行
```

多个域名用英文逗号分隔。然后：

```bash
cd server
docker compose up -d          # 注意：这里不用加 --build，改环境变量不需要重建镜像
```

重启后日志第一行会打印当前放行的完整来源列表，可以核对：

```bash
docker compose logs | grep 允许来源
```

### 一条不能碰的红线

**永远不要给前端的 `<audio>` 元素加 `crossOrigin` 属性。**

物种叫声是浏览器直接播放的，不走 fetch，本来就不需要 CORS。一旦误加了 `crossOrigin="anonymous"`，所有跨域音频会**整段静音**，而且控制台不报错，极难排查。代码里目前所有播放路径都没加，注释里也写了警告，改代码时别手贱。

## 九、模型拉不下来怎么办（离线方案）

### 症状

`/healthz` 返回 `"engine":"error"`，日志里有类似：

```
BirdNET 模型加载失败：... Connection timed out / SSL error ...
```

多半是服务器网络出不去，或者被墙了。

### 先确认不是别的问题

```bash
docker compose logs | grep -i -E "模型|error|failed"
```

如果报的是 `birdnetlib 导入失败` 或 `tflite`，那是依赖问题不是网络问题，重新 `docker compose up -d --build` 试试。

### 方案一：给容器配代理（最省事）

如果你的服务器有可用的 HTTP 代理：

```yaml
    environment:
      # ...原有配置...
      HTTP_PROXY: "http://代理地址:端口"
      HTTPS_PROXY: "http://代理地址:端口"
      NO_PROXY: "localhost,127.0.0.1"
```

```bash
docker compose up -d
docker compose logs -f          # 观察模型是否开始下载
```

### 方案二：手工把模型塞进挂载卷（彻底离线）

模型缓存挂在名为 `birdnet-cache` 的 Docker 卷上，对应容器内路径 `/root/.cache`。

**步骤 1**：在**一台能正常联网的机器**上（你自己电脑就行），先让它把模型下下来：

```bash
pip install birdnetlib
python -c "from birdnetlib.analyzer import Analyzer; Analyzer(); print('模型已下载')"
```

**步骤 2**：找到模型缓存目录并打包。

birdnetlib 的模型文件通常在 Python 包目录内，用这个命令定位：

```bash
python -c "import birdnetlib, os; print(os.path.dirname(birdnetlib.__file__))"
```

到那个目录下找 `.tflite` 结尾的文件（约 50MB）和配套的标签文件（`labels` 相关的 txt），一起打包：

```bash
cd $(python -c "import birdnetlib, os; print(os.path.dirname(birdnetlib.__file__))")
tar czf ~/birdnet-model.tar.gz $(find . -name "*.tflite" -o -name "*labels*")
```

同时也把 `~/.cache` 打包一份（有些版本缓存在这里）：

```bash
tar czf ~/birdnet-cache.tar.gz -C ~ .cache
```

**步骤 3**：传到服务器：

```bash
scp ~/birdnet-model.tar.gz ~/birdnet-cache.tar.gz 用户名@服务器IP:/tmp/
```

**步骤 4**：在服务器上把文件灌进运行中的容器，然后重启：

```bash
cd /path/to/SoundVerse/server

# 确保容器在跑（就算 engine 是 error 也没关系，进程是活的）
docker compose up -d

# 灌 cache
docker cp /tmp/birdnet-cache.tar.gz tinglai-recognize:/tmp/
docker compose exec recognize tar xzf /tmp/birdnet-cache.tar.gz -C /root

# 灌模型文件到 birdnetlib 包目录
docker cp /tmp/birdnet-model.tar.gz tinglai-recognize:/tmp/
docker compose exec recognize sh -c \
  'cd $(python -c "import birdnetlib,os;print(os.path.dirname(birdnetlib.__file__))") && tar xzf /tmp/birdnet-model.tar.gz'

# 重启让它重新加载
docker compose restart
```

**步骤 5**：验证

```bash
sleep 30 && curl http://127.0.0.1:8000/healthz
# 期望 engine 变成 ready
```

> 因为 `~/.cache` 是持久化卷，灌进去之后**容器重建也不会丢**，只需要做这一次。

### 方案三：接受兜底，先保证演示能跑

模型实在下不来也**不影响演示**。服务照样起得来，识别请求返回 503，前端自动走「离线示例结果」，主流程完整、页面不崩。

先把演示跑通，模型的事可以后面再解决。**别为了这个卡住整个进度。**

## 十、排障速查表

| 现象 | 原因 | 怎么修 |
|------|------|--------|
| `docker compose up` 报端口被占用 | 8000 端口已经有别的东西在用 | `sudo lsof -i :8000` 查是谁；要么杀掉它，要么改 compose 里的宿主机端口如 `"127.0.0.1:8001:8000"`（**冒号右边的 8000 不要动**，那是容器内端口） |
| 构建卡在 `pip install` 很久 | 拉 PyPI 慢 | 耐心等，或在 Dockerfile 的 pip 命令后加国内源 `-i https://pypi.tuna.tsinghua.edu.cn/simple` |
| `/healthz` 返回 `engine: error` | 模型没下下来 | 看第九章离线方案 |
| `curl 127.0.0.1:8000/healthz` 通，但外网访问不通 | 容器只绑了回环，反代没配好 | 回第四步；检查 `sudo nginx -t`、防火墙、云控制台安全组三处 |
| 浏览器控制台 CORS 报错 | 前端域名不在白名单 | 用 `EXTRA_ORIGINS` 追加，见第八章。**不要改代码** |
| 请求 404，路径里有两个 `/api/recognize` | `VITE_RECOGNIZE_API` 填成完整地址了 | 只填到域名为止，见第五步的对照表，改完**必须重新 `npm run build`** |
| 前端一直显示「离线示例结果」 | 后端没起 / 地址配错 / 没重新 build | 按第七章三级验证从里到外逐级排查 |
| 改了 `.env` 但没变化 | Vite 环境变量是构建时注入的 | **重新 `npm run build` 并重新部署 dist/** |
| 上传大文件返回 413 | nginx 默认 body 上限 1MB | 反代里加 `client_max_body_size 25m;` |
| 上传返回 400 `too_large` | 超过服务端 20MB 上限 | 截短音频；或改 compose 里 `MAX_UPLOAD_MB`（要和前端 20MB 限制一起改才有意义） |
| 上传返回 400 `bad_format` | 格式不支持 | 支持 wav / mp3 / m4a / ogg / webm / flac / aac / mp4，其它先转码 |
| 识别请求超时 | 冷启动第一次要加载模型 | 第一次慢是正常的，之后就快了。可调 `VITE_RECOGNIZE_TIMEOUT=60000`，并确认 nginx 的 `proxy_read_timeout` 够大 |
| 识别出物种但没有科普卡 | 映射表里没这条 | 在 `src/data/recognition-map.json` 补映射（属数据维护范围，找林知声） |

## 十一、一页纸速查

```bash
# ① 拉代码
cd /path/to/SoundVerse && git pull origin main

# ② 起服务
cd server && docker compose up -d --build
docker compose logs -f                       # 看到「识别引擎就绪」即可 Ctrl+C

# ③ 验证服务
curl http://127.0.0.1:8000/healthz           # 要看到 status: ok

# ④ 配 nginx 反代 /api/ → 127.0.0.1:8000（见第四章方案 A）
sudo nginx -t && sudo systemctl reload nginx
curl https://tinglai.dushiofcourses.cn/healthz    # 外网也要通

# ⑤ 配前端环境变量（仓库根目录，注意只填到域名）
cd /path/to/SoundVerse
echo 'VITE_RECOGNIZE_API=' > .env            # 同域名反代就留空

# ⑥ 重新构建并部署
npm run build
sudo cp -r dist/* /var/www/tinglai/

# ⑦ 浏览器实测
# 打开 https://tinglai.dushiofcourses.cn/#/recognize
# F12 → Network → 录音识别 → 看 recognize 请求是不是 200
```

### 验收清单

- [ ] `docker compose ps` 显示容器 `Up`
- [ ] `curl 127.0.0.1:8000/healthz` 返回 `status: ok`
- [ ] `engine` 字段是 `ready` 或 `lazy`（不是 `error`）
- [ ] 外网 `curl https://域名/healthz` 也通
- [ ] 浏览器能打开 `https://域名/docs`
- [ ] 仓库根目录 `.env` 里 `VITE_RECOGNIZE_API` **没有**多写 `/api/recognize`
- [ ] 改完 `.env` 后重新跑过 `npm run build`
- [ ] 前端录音识别返回 Top-3，且结果里**没有**「离线示例结果」标识
